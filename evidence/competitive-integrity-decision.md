## Actual path and expected-frame rule

1. Device/OS → companion or native keyboard state → Warcraft. Delays before SDL observation or the map's first local poll are outside the retained native measurements. The companion at commit `fa46569e56d751b7e805dc5c57339155b96bea5b` currently logs SDL events, drains the event queue, samples current pad state once, then delivers mapped keys; it does not send a timestamped input record into the map. In wc3-melee:companion/src/main.rs, button-down/up events are logged but do not update the mapper individually. A complete queued cycle ending neutral can therefore be observed in SDL yet absent from keyboard delivery. The loop requests a 4 ms sleep after focus checks/output; that is not a maximum sampling gap. This is code-established, not a measured physical-controller loss rate. Whether a short cycle should affect gameplay requires the independent sampling rule; ordinary subframe quantization is not automatically a defect.
2. `wc3-melee:wurst/Melee.wurst` calls `BlzIsKeyPressed` from the requested 60 Hz service. This is the first observable keyboard state in the current map. Device transitions entirely between those observations are absent.
3. `wc3-melee:wurst/ShadowInputSchedule.wurst` assigns the sample once to **local next speculative frame F + fixed D**. D=0 currently. This is a progress cursor, not a calculation from a device timestamp or an independently aligned continuous clock. Initial D rows, when used, are neutral. Repeated sampling at the same F cannot overwrite its assigned row.
4. The sampler latches one pressed and one released bit per action until a row commits. It can retain an observed edge while F waits, but repeated same-action edges and their ordering coalesce. A wholly unobserved tap is not retained. Direction/special metadata has the same observation boundary.
5. `BlzSendSyncData` carries epoch, absolute frame and normalized input; `GetTriggerPlayer` identifies the sender. Identical duplicates are idempotent, conflicts are rejected, and arrival order does not change frame tags. Common K advances only through contiguous complete rows for every active participant.
6. Each service callback captures, runs up to six confirmed rows, reconciles retained speculative history, then advances at most one speculative row. Missing remote input predicts prior holds without fresh edges. Own pending input can drive local prediction before native echo.
7. Replay restores the snapshot preceding the first differing row and executes stored input without repolling, resending or presenting intermediate replay states. Predicted poses and confirmed event-bearing effects/audio have different presentation timing.

For a continuously advancing frame contract, the independent oracle must be defined before capture: an agreed epoch and sampling boundaries on an aligned clock, with fixed D and documented boundary uncertainty. For an agreed pause contract, the oracle must identify the common paused interval and resume rule. **Elapsed wall time alone does not prove that a paused game chose the wrong frame.** The current code does not demonstrate either contract's physical-input fidelity through an asymmetric service stall.

These narrow the current implementation's input-preservation failure without
establishing an unavoidable engine limit. Competitive recommendation stays HOLD.

The headless oracle is the authored corpus's fixed frame index, independent of the schedule's eventual choice. Four logical frames of delayed delivery are **not** a measured 66.67 ms native packet delay.

Retained native trials identify each injected event by trial/edge and bracket submission with the same Linux monotonic clock used to anchor both captures. The first changed captured frame estimates visible response; approximately 16.4 ms capture spacing limits temporal precision. Native game time is a separate clock and may pause; it is not substituted for host wall time. No cross-machine latency is calculated by subtracting unsynchronized clocks. Controller hardware, OS service before injection, physical scanout and human perception are bypassed.

The native samples are mostly held Q presses, not coverage of rapid taps, simultaneous combat buttons and independently expected near-boundary frame assignment. Those gates remain open. The induced missing tap is one diagnostic event, not a population loss rate. A maximum observed in a small sample is not a guaranteed bound.

## Acceptance criteria and verdict

1. Define expected frame independently of the assigned row: shared epoch, sample boundary, fixed delay, clock uncertainty and pause/resume rule. Normal boundary quantization may choose the adjacent permitted sample; unexplained four-frame shifts are not acceptable.
2. In the declared supported envelope, no unexplained missing required events, duplicate application, original-row retargeting or confirmed disagreements. Include repeated presses/releases, held directions, rapid taps, simultaneous buttons and near-boundary timing. Preserve event IDs through capture/assignment/receipt/application. A useful first native gate is at least 1,000 scripted transitions across both roles; zero failures there is still an observed result, not a universal bound.
3. Repeat the contact case natively with the same original F5 defense delayed four frames, both roles and realistic load; verify final resolved outcome and record each player's temporary correction. Test beyond R with explicit stop/resume semantics. Rendering hitches and gameplay clock changes must be distinguished.
4. Keep the existing development response targets: local visible median≤33 ms, p95≤50 ms, p99≤83 ms, without recurring unexplained>100 ms responses. Physical-controller measurements are separate. Current combat press median and release p95 do not meet all those targets; minimal-probe success cannot substitute for combat acceptance.
5. Validate native controller consumption and the selected two-client online path on the same artifact. Required macOS/Windows/Linux, GameCube and Deck claims need their own native gates.

**Today:** we can honestly claim a working deterministic frame-based fighting model and tested correction of received, originally tagged late input, including a contact-changing shield example. We also have a demonstrated pre-capture omission under one induced native outage and measured visible timing variability.

**Development target:** a competitive experience remains a plausible target if supported capture can preserve intended common frame identity and the native presentation gates pass. Evidence does not support a full-throated greenlight yet.

**Cannot promise:** Slippi-quality native input timing, arbitrary spike resilience, absence of role advantage, physical controller latency, seamless corrections, continuous analog ingress or native support on all three platforms.

**Character design:** begin provisional character frame data against the deterministic 60 Hz simulation, with startup/active/recovery/physics measured in logical frames. Do not assume every logical frame always consumes 16.67 ms of wall time during a pause, nor freeze reaction windows, one-frame exchange promises or online balance around guaranteed input latency. Pause dependent competitive commitments; do not compensate for unexplained timing by quietly widening all character windows.

The next decision-changing experiment is the native capture/frame bridge and common-clock/pause contract, followed by the recorded contact replay on two native clients. There is no need to spend this investigation building a matchmaking platform or general benchmark framework.
