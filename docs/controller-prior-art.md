# Controller reuse decision — 3 October 2026

Use a Rust core with **SDL3 for controller discovery, normalization, hotplugging and supported device protocols**, **enigo for keyboard delivery**, and native platform APIs for foreground game identity. The companion must work on macOS, Windows and Linux. Keep Tauri outside the input delivery loop and retain the existing AntiMicroX profile as the observed digital baseline. The [cross-platform decision](controller-platforms.md) specifies the Windows, macOS and Linux output paths and required native trials. Use the C# project as a behavioral reference; SDL3 already supplies GameCube adapter handling.

This recommendation concerns input acquisition and local key delivery. None of the inspected projects supplies a ready-made continuous-analog bridge into this Warcraft map. Reading an analog axis on Linux does not make it available to Wurst, and neither controller support nor Slippi reuse establishes Warcraft engine or multiplayer latency.

## What the cited projects actually do

**Blizzard Controller Support** at `eaef1ffa124869d661eb576c8f75009b9ea08f19` polls MonoGame's `GamePad.GetState`, translates buttons/sticks into keyboard and mouse actions, and calls SharpHook's `EventSimulator`. Its left stick moves the cursor; its right stick produces camera keys. It is a controller-to-desktop-input application with game-specific overlays, not a native Warcraft controller API, injected game module, or analog map transport. Source: [controller state](https://github.com/erfg12/Blizzard_Controller_Support/blob/eaef1ffa124869d661eb576c8f75009b9ea08f19/Controller/Input/ControllerState.cs), [simulation](https://github.com/erfg12/Blizzard_Controller_Support/blob/eaef1ffa124869d661eb576c8f75009b9ea08f19/Controller/Input/InputSimulator.cs), [mapping](https://github.com/erfg12/Blizzard_Controller_Support/blob/eaef1ffa124869d661eb576c8f75009b9ea08f19/Controller/Classes/ControllerInputs.cs).

Its .NET 8 core declares MonoGame 3.8.4.1, SharpHook 6.2.0 and configuration/resources packages 9.0.7. The UI declares Avalonia 11.3.2 and CommunityToolkit.Mvvm 8.2.0. Linux native window calls use X11. The [UI input task](https://github.com/erfg12/Blizzard_Controller_Support/blob/eaef1ffa124869d661eb576c8f75009b9ea08f19/Controller_v2/App.axaml.cs) waits 16 ms per iteration; button processing also sleeps 10 ms, and other branches contain additional waits. These are source facts, not measured latency. The shown input task gates on controller connection, not exact foreground-game identity. Its `IsGamepadButtonPressed` currently aliases held state. Do not borrow its timing, edge semantics, or process-exists check as a competitive-input design. No license file was present in the clean inspected checkout. **Public source permits factual investigation, not translation or code/asset derivation.** Its demo is useful evidence that OS input mapping is a viable approach; the demo was not independently reproduced here.

**AntiMicroX** at `7939b51173826959736fc18773b0610460d9d504` (3.5.1) already implements SDL2-based controller mapping, profiles, XTest and Linux uinput output. The existing original bindings in smashcraft:tools/controllers/xbox.amgp are the shortest reusable baseline. Their documentation distinguishes mapping/recognition from physical response. An earlier project test exercised the digital mapping; this research did not rerun it. The [README](https://github.com/AntiMicroX/antimicrox/blob/7939b51173826959736fc18773b0610460d9d504/README.md) explicitly excludes Wayland auto-profiles. Its [auto-profile watcher](https://github.com/AntiMicroX/antimicrox/blob/7939b51173826959736fc18773b0610460d9d504/src/autoprofilewatcher.h) checks every 500 ms: observed profile switching is not an immediate focus-loss guarantee.

Reuse AntiMicroX as an **unmodified external application plus original profiles**, while useful. Do not embed its GPL implementation in a differently licensed Rust core. A launcher can invoke an installed executable and select configuration through supported interfaces; distribution of the GPL executable still entails its notices and corresponding-source obligations. Merely using a separate executable/configuration does not justify copying its implementation. A built-in Rust path is warranted for explicit focus handling, traceability, action aggregation and eventual map integration, not because existing mapping is absent.

**Slippi** separates an Electron launcher from a modified Dolphin emulator. [Launcher documentation](https://github.com/project-slippi/slippi-launcher/blob/0930a2b66bdda78cebd0444c5e56249fea516cbe/README.md) describes updating/launching Dolphin and replay features. Its adapter input is in [Slippi Dolphin's GCAdapter](https://github.com/project-slippi/Ishiiruka/blob/60f7b63496fb6ec7b9180a04f16f3edc0ad89fe2/Source/Core/InputCommon/GCAdapter.cpp), with emulator configuration, serial-interface and timing dependencies. This is valuable prior art for device handling and separation of launcher from game runtime; it is not a standalone Warcraft bridge or transferable proof of rollback/latency. No emulator or launcher code needs importing for the selected path.

## Which input layer to reuse

| Candidate | Deciding evidence | Decision |
| --- | --- | --- |
| SDL3 through Rust `sdl3` | Unified gamepad API, mapping database, hotplugging, explicit Steam Deck and GameCube HIDAPI drivers. The GameCube driver already handles four adapter ports, both sticks, analog triggers and trigger clicks. | **Choose.** Covers the requested device families with one maintained abstraction. Native SDL dependency is an acceptable tradeoff. |
| `gilrs` 0.11.2 | Rust API, familiar button names, SDL2 mapping format, hotplugging, rumble; Linux reads evdev, Windows defaults to WGI with XInput available. | Good alternative for OS-exposed gamepads. It does not itself solve a raw adapter that has no usable evdev gamepad. Avoid a second acquisition stack initially. Its README also notes WGI foreground-window requirements, relevant to companion applications. |
| `evdev` 0.13.2 | Handles Linux input events, dropped-event synchronization and uinput. README explicitly says it has no gamepad button normalization abstraction. | Reuse **for a Linux uinput output backend if needed**, or exact raw-event diagnosis. Do not recreate SDL's device/mapping layer on top of it. |
| `hidapi` Rust wrapper | Supported HID enumeration/read/write and selectable Linux hidraw/libusb backends. No controller meaning or mapping layer. | Reserve for a demonstrated unsupported HID capability; not needed alongside SDL's existing GameCube driver. |
| `rusb` 0.9.4 | Rust API over libusb, interface claiming and USB transfers. No controller protocol. | Reserve for a demonstrated raw USB capability absent from the chosen library. Not the first GameCube implementation. |

The [SDL header](https://github.com/libsdl-org/SDL/blob/4a17e772ea9a4ff77dd10fa6ea6f45fc6731eb01/include/SDL3/SDL_gamepad.h) defines positional gamepad controls and background-input configuration. Set background acquisition deliberately because Warcraft, not the companion, must own focus; independently gate output. Pump SDL events on its supported owning thread. The Rust binding's main-thread restriction is explicit; do not simply move an event pump to an arbitrary Tauri worker thread. A UI-less core proves this boundary before UI integration.

Use SDL's mappings and, when needed, the maintained [SDL_GameControllerDB](https://github.com/mdqinc/SDL_GameControllerDB/blob/c1d5289a1f713b30a2c121e9fe6529d39360be0f/README.md), which documents SDL3 loading. Do not maintain device GUID tables by hand. Physical labels and game actions remain distinct: Xbox **X=special, B/Y=jump, RB=grab, LT/RT=shield; stick-up=tap jump**, A=attack, LB=walk/tilts and right stick=C-stick actions. A GameCube preset uses its own B=special, X/Y=jump and Z=grab. Do not mechanically transfer letter labels between pad families.

## GameCube adapters and Steam Deck

The selected [SDL GameCube driver](https://github.com/libsdl-org/SDL/blob/4a17e772ea9a4ff77dd10fa6ea6f45fc6731eb01/src/joystick/hidapi/SDL_hidapi_gamecube.c) contains Nintendo/Wii U and supported third-party handling, PC-mode handling, adapter initialization, four-port hotplugging and rumble. Its Nintendo-format packets begin with 0x21 and contain four nine-byte port records; initialization uses 0x13 and rumble uses 0x11. These are factual protocol observations, **not a reason to rewrite the parser**. Both SDL's permissively licensed implementation and Dolphin's separate libusb implementation establish that this is already solved upstream.

A generic USB GameCube pad or adapter in PC mode may expose ordinary OS gamepad input. A Nintendo-compatible Wii U mode adapter instead exposes device reports requiring initialization and per-port interpretation; do not assume it appears as four normal evdev devices. On Linux the build/device path may use hidraw or libusb and needs access to the applicable device, not blanket privileged execution. On Windows/macOS the driver/backend and device access differ; Dolphin's direct USB path is not proof that the exact SDL build can open the same adapter with the same installed driver. In particular, do not replace a Windows device driver merely to make a speculative backend work. First identify VID/PID, mode, active OS exposure and SDL's selected driver on the actual adapter. None was physically tested here.

The GameCube driver rescales axes using tracked minimum/maximum values, including separate trigger initialization. Therefore normalized SDL values are **not untouched original console bytes or proof of exact Melee calibration**. This is sufficient for the immediate digital mapping thesis. If a later named requirement needs raw values or exact calibration, first demonstrate that gap and address the upstream capability; do not silently add a consumer-side decoder or compensate with guessed constants. Rumble capability is also conditional: the source checks the second adapter USB cable and excludes WaveBird rumble.

SDL has a dedicated [Steam Deck driver](https://github.com/libsdl-org/SDL/blob/4a17e772ea9a4ff77dd10fa6ea6f45fc6731eb01/src/joystick/hidapi/SDL_hidapi_steamdeck.c). Steam Input may instead present a virtual controller, or already synthesize desktop input. Select one delivery path and explicitly check for duplicate physical/virtual input when testing SteamOS desktop and gaming sessions. Do not map through both Steam Input and the companion simultaneously by accident. Xbox recognition under the present Linux driver and existing SDL2 trial does not establish Steam Deck controls, focus behavior, or response.

## Output and focus boundary

For the currently used Warcraft under Proton/XWayland, retain **XTest on the correct X display** through enigo's maintained X11 backend; `x11rb` remains a native API reference. XTest sends input through that X server; it is not an injection API for arbitrary native Wayland clients. Conversely, SDL's ability to read a controller does not solve desktop injection or focus.

Arm only for the exact intended Warcraft window/instance, corroborated with the compositor's actual active-window state on the current desktop. An X11 title/process-exists match alone is insufficient when a Wayland-native window, overview, or lock screen can own input. Two clients also require explicit target identity; a shared game title does not choose a participant. On loss of eligibility or disconnect, clear owned held actions and require a defined neutral/rearm transition. Keep references/counts for shared actions: releasing LT must not release shield while RT remains held; releasing B must not cancel a still-held Y/up jump source. Coordinate with the existing keyboard path rather than assuming independent keys cannot overlap.

Linux uinput produces a virtual input device and can work through Wayland, but is not per-window addressing or focus authorization. Use existing `evdev` APIs if this output backend becomes necessary, with scoped device access and the same independently resolved focus policy. The [RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) provides session-mediated input and an EIS connection where supported; it is a possible compositor-supported route, not a universal background-input permission. Portal support and foreground identity remain runtime/compositor questions. The existing XWayland path is the immediate target; native Wayland support requires an actual consumer test before being advertised.

The owned code should therefore be small: action bindings and thresholds, held-source aggregation, tap-jump edge/rearm behavior, exact-client eligibility, and delivery/diagnostic timestamps. Retain distinct raw/normalized values in the diagnostic sample. Tauri can edit settings and display controller status later; it should not clock input through webview messages.

## Smallest discriminating executable experiment

Build one UI-less Rust experiment using SDL3 plus enigo on the existing X11 path, then run it under the controlled native test sessions. No clients, focus, mapper or devices were changed during this research.

1. Enumerate the wired Xbox through SDL; record identity, selected mapping and normalized axes/buttons. Enable background acquisition. Use the current Warcraft keyboard preset and the requested bindings above.
2. Run only one mapper output path at a time. Target the already-running intended client. Log controller events, action transitions, focus eligibility and emitted key transitions with a monotonic clock. Preserve the current game-side capture/trace for correlation.
3. Exercise X special; B and Y jump; stick-up tap jump; each trigger and **LT+RT held together followed by one release**; RB grab; then one focus-away/return and one controller disconnect. Verify actual map actions and neutral release. Compare the identical digital path with the current AntiMicroX baseline once.
4. If SDL sees the Xbox and the Rust path reproduces the actions/releases safely, keep SDL and proceed to the separately unresolved analog map-ingress experiment. If acquisition fails, resolve its exact device/backend cause upstream; if emitted keys do not reach the map, investigate the display/focus/injection seam. Do not switch controller libraries to cure an engine transport failure.

The result distinguishes whether the selected reusable stack works in **this** WC3 session. Software event-to-key timing is not physical button-to-pixel latency, nor network latency. A later physical GameCube/Steam Deck run validates those devices; synthetic devices can check software semantics only. Continuous analog requires its own smallest map-ingress proof before packaging or promising analog play. No new executable was compiled or run by this worker.
